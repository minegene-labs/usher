# Architecture

How Usher is put together. Terms are defined in [glossary.md](glossary.md).

```
iPhone / iPad / Mac ──HTTPS──▶ reverse proxy :443 ──▶ Usher 127.0.0.1:8484 ──▶ Sonarr, Radarr, Prowlarr, Transmission, Jellyfin
```

## Server (`usher/`)

Python standard library plus `cryptography` (for Web Push). One process that:

- **Polls the integrations** (`state/`, `clients.py`) and turns what they say into plain states: Asked, Found, Downloading, Getting it ready, Ready to watch.
- **Does what people ask** (`actions.py`, with search in `search.py` and retry and stop in `stop_actions.py`): search, Get it, seasons, retry, stop, remove; `replace.py` swaps stalled downloads for healthier copies, `tidy.py` finds watched titles to remove.
- **Keeps one identity per title** (`titles.py`) across Sonarr, Radarr, Jellyfin and the requests, and sends every open device a `changed` live update when anything about a title changes.
- **Serves HTTP** (`server.py`): the web client's files, a JSON API under `/api/`, live updates as Server-Sent Events, a poster proxy and `/healthz`. Sign-in, sessions and throttling are in `auth.py` and `store.py`.
- **Discovers** (`discover.py`, `discover_rows.py`, `picks.py`): TMDb lookups, streaming availability, Discover's rows, built in the background and kept on disk; each account's own Picked for you, from its likes and requests, kept in memory only.
- **Notifies** (`notify.py`, `push.py`): decides who is told what, and sends Web Push.
- **Checks itself** (`wiring.py`, `diagnostics.py`): every ID Usher points at, Status details and Logs.
- **Reads settings** (`config.py`) from `usher.toml`; `cli.py` is the `usher-user` command.

## Web client (`web/`)

A Progressive Web App: one custom element, plain CSS and ES modules, no framework and no build step. `web/data.js` is the only way the client calls the server and holds every list the app keeps; each screen is a mixin in its own module, assembled by `web/app.js`. A service worker (`web/sw.js`) keeps the app shell and the artwork (`/api/art/`, capped, least recently shown dropped first) on the device; every other `/api/` request goes to the network. The app keeps the last copy of its lists and of Home and Status in Cache Storage, per account, shown only after the server confirms the session and deleted on sign-out (`lists.restore` in `web/data.js`).

## Data flow

1. A person taps **Get it**; the server records the request, adds the title to Sonarr or Radarr and searches.
2. Sonarr or Radarr picks a release through Prowlarr's indexers and hands it to Transmission.
3. The poller reads the queue, Transmission's progress and Jellyfin's library, and derives the state the person sees.
4. Each change goes through the title's identity, which drops the server's stale copies and tells every open device to refresh.

## Data

Accounts, sessions, requests and each account's likes and dislikes (`opinions`, deleted with the account) are in SQLite at `data/usher.db` in the install folder; Discover's last rows (public TMDb data only) in `discover.json`; titles kept out of Tidy up in `kept.json`; the Web Push key in `vapid.pem`. Every file Usher writes goes through `usher/files.py` (mode 0600, fsync, atomic replace).

## Upstream check

The Upstream check workflow starts the latest official image of each integration every Friday, and the announced betas on the first of each month. It runs the calls Usher makes and the fields it reads (`tests/upstream_check.py`). When a latest image fails, one issue labelled `upstream` names the app, version and call, and closes by itself on the next green run; the monthly beta run only comments, on one standing issue. Each new version of an app the latest run sees opens one issue, `Support <App> <version>`, labelled `upstream-release` and `P1`, with the previous version, the release notes and whether the calls passed on it (`tests/upstream_releases.py`). The issues are the record of the versions seen: found by label and title, so a rerun opens no second one, and a version older than one already seen (an older image chosen by hand) opens none. The issue closes as verified once every call passes on its version, with its row for the support matrix in the comment, and as superseded when a newer version of the same app comes out, so at most one is open per app. Every real answer is kept for 30 days as a run artifact: the source for refreshing the fixtures in `tests/mock_apps.py`. The versions of the last green run are what `python3 -m tests.upstream_report matrix results.json` writes into the support matrix in README.md. The lists in the seeded apps start empty, so item fields are not checked yet.

## Vulnerability checks

The Weekly checks workflow runs pip-audit on `requirements.txt` (pinned in `requirements-audit.txt`, kept out of the image and of a pull request's run) and Grype on the image it builds. `.github/scripts/vulnerabilities.py` keeps the findings that have a fix available and drops those accepted in `.github/accepted-vulnerabilities.toml` until their expiry date. Anything left, or an expired acceptance, opens or updates one issue labelled `vulnerabilities` and fails the run; a clear run closes the issue, as Upstream check does.

## Merge report

Release has three jobs. `promote` moves `stable` to the tested commit and publishes the release; it alone can write to the repository's contents. `image` then builds the version's container image for `linux/amd64` and `linux/arm64` (the arm64 half under emulation), pushes it to GitHub's container registry tagged with the version and `latest`, and attests its build provenance; a version that already has its image builds nothing, and the job can publish a package but not write to the repository. `report` then runs `.github/scripts/merge_report.py`, also when `promote` or `image` failed, which reads the merge from GitHub's REST API, and comments the result on the merged pull request and in the job summary: a verdict line, `OK` or `PROBLEM`, then one line per check. The checks: `promote` and `image` finished (a failed image job is a problem: the version's image may be missing), the version is released at the merge commit (a merge that changes only files outside `usher/`, `web/`, `deploy/`, `tests/`, the `Dockerfile`, `requirements.txt` and `CHANGELOG.md` needs no new version), `stable` is at it, the issues it fixes are closed, and every open issue a maintainer has had time to triage has a priority label. Issues the repository opens by itself (labelled `upstream`, `upstream-beta`, `upstream-release` or `vulnerabilities`) and issues opened in the last 24 hours are left out of that check. Changed files that need a person's eye (workflows, the `Dockerfile`, `deploy/`, the coding-session settings folder, `web/sw.js` beyond its version line, `web/data.js`) are listed without counting as a problem. A `PROBLEM` opens or updates one issue labelled `bug` and `P1`, "Merge problem: PR #<n>", and turns the run red. The next `OK` closes that issue. The issue is found by its title and both labels, so no other issue is updated or closed, and one report runs at a time (the `release-report` concurrency group), so two quick merges don't open two issues. Each run reports the commit it was called for: a merge whose Release run never starts, because a later merge superseded it while it waited or `main` had already moved on, isn't reported; the next merge's report covers `stable` and the open issues again. The job can comment and write issues but not contents; Tests and Auto-merge grant Release the sum of the three jobs' permissions.

## Deployment

A container built from the `Dockerfile` and run from `deploy/compose.yaml`; the server deploys the `stable` branch by itself. Everyone else runs the published image from `compose.yaml` at the repository root, which mounts nothing from the machine. See [deploy/README.md](../deploy/README.md).
